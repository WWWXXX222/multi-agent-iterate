# Multi-Agent Iterate

让多个 agent 主动检查问题的拆解方式、提出具体改法，再由一个主控裁决、修订和验证，减少你逐轮提供 feedback 的负担。

适用于产品方案、研究报告、设计、代码实现和公司规划。它是一个负责组织协作的 skill，按任务需要调度子 agent；具体规则见 [SKILL.md](SKILL.md)。

## 快速开始

安装后，在 Codex 中附上现稿或提供文件路径，然后直接说：

```text
用 $multi-agent-iterate 改善这份方案，最多 3 轮。
保留已确认的预算、上线日期和目标范围。
检查是否有更清楚的分类、层级或推进方式，重要建议要给出具体改法。
自行修订和验证，最后给我推荐稿、改动依据和关键待决项。
```

最好提供四项信息：**想交付什么、现有材料、不能改变的约束、迭代上限**。已有的测试或验收标准也可以一起给出；主控会先明确如何判断结果是否改善。

## 它如何工作

先确定目标、约束和验收条件，再按任务选择流程：

| 任务状态 | 采用的方法 | 示例 |
| --- | --- | --- |
| 方向未定 | **Arena：独立提案**，比较后选一个底稿，吸收兼容的优点 | 比较两种产品方案或报告结构 |
| 方向已定、工作可拆开 | **Swarm：分工执行**，划清文件或交付物边界，再整合验证 | 并行完成接口已确定的几个模块 |
| 已有稿件 | 判断是否需要结构挑战，再独立评审、裁决和修订 | 改善策略、文稿或现有实现 |
| 只需要评审 | 独立评审后交付问题与判断 | 找出方案漏洞，保留原稿 |

复杂且开放的任务，第一轮先加入 **结构挑战 → 具体改法 → 价值判断**：一位 agent 从原始需求和事实独立拆解问题，先不看现稿的可变框架；另一位独立检查现稿，主控比较两者。用户已确认的目标和约束继续保留，分类、层级、顺序和解法可在授权范围内调整。

例如路线图中，不同目的、成熟度或验收方式的工作混排，可能影响投入决策。Agent 应说明哪里混淆、怎样拆分或重组、原条目如何承接，以及如何证明改后更好。具体分类从任务资料产生；交叉工作可以用主分类和依赖表达，避免重复计数。

这一环节计入原有轮次和 agent 预算。已有清晰框架或只改名称、顺序、局部 bug 时可跳过。没有明确收益就保留原结构，不要求每轮都提出新概念。

随后每一轮完成以下循环：

**独立评审 → 主控裁决 → 修订或有理由不改 → 按相同条件验证 → 保留有效结果。**

重要反馈必须包含 **发现 → 对目标的影响 → 具体改法 → 验证办法**。主控读取实际产物，比较收益与代价，决定哪些意见采纳、哪些拒绝、哪些仍待核实。验收结论对应最终版本；整合或修改后，受影响的部分需要重新验证。

## 走偏时怎样恢复，纠正后怎样复用

- **计划也包含验证**：复杂任务提前明确实施步骤、验证方法和所需环境；简单修改直接处理。
- **前提失效就重规划**：暂停依赖错误前提的步骤，查证后更新计划和相关 agent 简报，保留有效工作；轮次与预算继续累计。
- **主动完成修复**：在授权范围内自行查来源、日志或复现，修复后重新验证；方案简化需保留原有目标与约束。
- **经验用于下一次执行**：把可复用纠正记成“适用条件、证据、下次动作、验证方法”，下次相关任务读取，合并重复项、修正失效经验。

这些做法吸收了 Boris Cherny 的公开分享与 Claude Code 官方文档，并针对文档和代码任务做了适配。复用已有项目记录即可，不强制新建 `tasks/todo.md`、`tasks/lessons.md` 或增加逐步确认。细节见 [重规划与经验复用](references/planning-and-learning.md)。

## 文档和 coding 怎样分别验收

| 任务 | 重点检查 |
| --- | --- |
| 文档与方案 | 事实和约束准确；分类、层级与取舍合理；读者能完成实际决定或行动；表达简洁、术语一致 |
| Coding | 用户路径和接口正确；相关测试、错误路径及回归通过；性能或交互要求有实际运行证据 |
| 混合任务 | 内容与实现分别验收，再核对展示、交互或导出是否忠实保留内容；一侧通过不能掩盖另一侧失败 |

文档开始前会从你的需求、明确反馈和认可样例提取简短的质量约定。例如 OKR 要区分 O 的方向与 KR 的可验收结果；缺少数值时先写清指标、单位和测量方式，目标值标待定，避免强行编出百分比。已有信息能解决的问题自行处理，关键取舍集中交给你。

文稿验收不能保证经营结果，测试通过也需要与真实需求对照。未知事实和外部验证缺口会在交付时注明。具体检查见 [任务验收](references/task-acceptance.md)。

文档迭代保留可辨认的版本、相邻差异与恢复入口；无改动的一轮只记复核。复用现有版本方式，不必搭建新系统。详见 [文档版本与回退](references/task-acceptance.md#文档版本与回退)。

## 默认运行方式

| 项目 | 默认设置 |
| --- | --- |
| 候选方案 | 方向未定时，2 个独立候选 |
| 修订轮数 | 最多 3 轮，可由你指定 |
| 独立评审 | 复杂结果安排 2 个独立评审上下文 |
| 结构挑战 | 按需在第一轮进行，复用评审名额；后续有新证据或明显停滞时再判断 |
| 模型 | 继承当前可用模型；同模型独立上下文也可以运行 |
| 并发 | 按环境能力和任务需要安排，可分批执行 |
| 停止条件 | 达成验收、完成指定轮数、达到资源上限，或默认流程连续 2 轮无实质改善 |

你的明确要求优先于默认值。精确指定“两轮”时，会完成两轮复核，但不会为了凑轮数强行改稿。没有子 agent 能力时，会披露限制并顺序完成可做的工作。

只有会影响方向、缺少必要授权，或无法从资料和验证中解决的取舍，才需要你介入。未知事实和未经确认的指标会保留为待核项。

## 最后会得到什么

- **推荐结果**：可以直接审阅的最终稿或实现。
- **改动依据**：修复了什么，哪些建议未采纳，以及理由。
- **验证证据**：实际检查、测试或原始资料对照，说明本次能验证到哪里。
- **运行记录**：实际 agent 配置、轮次、停止原因和关键待决项；复杂任务留有检查点，便于继续。

结果会注明质量状态：`VERIFIED` 表示约定的验收已通过；`CONDITIONAL` 表示仍有外部条件或待决项；`INCOMPLETE` 表示必要工作未完成。到达轮次上限本身不代表通过。

## 其他调用示例

**比较方案**

```text
用 $multi-agent-iterate，基于这些资料独立提出两个方案，
比较后选一个，说明取舍，并验证整合后的版本。
```

**只做评审**

```text
用 $multi-agent-iterate 评审这份策略，重点检查证据和执行可行性。
只交付问题与主控裁决，先不要修改原稿。
```

**继续上次的工作**

```text
用 $multi-agent-iterate 继续这个运行目录里的任务。
读取 run.md 和现有产物，从未完成的步骤接着做。
```

更多场景见 [使用示例](references/examples.md)。只改名称、顺序或一句话时，直接修改并核验即可。

## 如何检验这套方法有没有进步

维护 skill 时，可用反馈发生前的稿件和资料回放，隔离后续反馈及答案，检查它是否主动发现关键问题、给出可执行改法、保留约束，并避免无收益重构。用于写规则的案例属于回归案例；检验主动发现能力需要另选未参与制定规则的案例。要声称新版优于旧版，需在相同输入和预算下实际对照运行。

评价看问题、证据和实际改进，不要求复述用户答案或得到更高的自评分。可另选不同任务和小修改检查适用范围。详细方法见 [回放验证](references/verification.md#skill-维护时的回放验证)；一次成功不构成稳定效果保证，普通业务迭代也不会自动附带这套评测。
