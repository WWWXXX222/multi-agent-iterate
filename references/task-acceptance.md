# 按任务选择验收

在建立运行契约和最终验证时读取相关部分。一个主控复用同一迭代循环，文档、coding 与混合任务各自保留验收证据。

## 文档与方案

先从需求、已有反馈及认可样例提取简短的质量约定：给谁看、帮助做什么决定或行动、必须保留什么、允许调整什么、如何表达。区分本次硬要求与可调整偏好；资料足够时自行形成约定，不重复向用户索取已知信息。领域规则按需引用，不把某家公司的写法推广到所有文档。

| 层面 | 检查方式 | 边界 |
| --- | --- | --- |
| 事实与约束 | 对照原始资料和明确决定；核对名称、数字、单位、范围、期限及责任状态 | 未知留待核；不能靠模型一致意见补造事实 |
| 结构与业务判断 | 比较分类、层级、优先级、依赖及资源假设；必要时运行结构挑战 | 给理由和取舍；没有数据不能保证业务目标合理或可实现 |
| 表达与使用 | 检查术语、简洁度与信息层级；让未起草者依据文稿回答真实读者问题 | 评审者模拟阅读要如实标记，不能声称已做真实用户测试 |

阅读检查可以问：哪些是本期优先项？哪些尚未决定？应如何验收？核心段落能否支撑这几个判断？盲看基线与新版本时，要求指出具体差异，不只投票选“更好看”的稿件。

按复杂度分配事实、业务、编辑三个视角，可由既有评审者兼顾；不强制新增三个 agent。先修影响决策的结构和内容，再润色。长文、短文、叙事和管理文档的表达要求不同，不强制全部改成表格或 bullet point。

### OKR 等管理文档的具体检查

- O 表达方向和要改变的业务状态；KR 承载可验收结果。是否进入公司层级取决于战略重要性与跨团队影响，不由材料中是否单独成章决定。
- 拆分或合并须保留各自的结果、责任和验收关系；不能用总完成率掩盖独立子结果失败。事实允许时质疑重复目标、容量冲突和先后依赖。
- 指标写清定义、单位、基线或比较对象、目标值及状态、期间、分母（适用时）与证据入口。缺少数值可用 `待定`；用户要求 `xx%` 等占位时保留其意图，仍需区分比例、时长、金额和次数。必要的定性结果可用可观察的通过条件验收，不强制虚构数字。
- 分开已确认目标与建议目标，统一同类术语，双语保持含义和口径一致。主文简明，验收细节按需展开。

文稿验收通过只说明约定范围内的质量；任命、资源、预算和经营效果需要真实依据，保留条件状态。

## Coding 与交互实现

先确定实际用户路径、已有接口与约束、失败样例和有关测试。结构挑战关注有证据的边界、依赖或替代解法；局部 bug 修复不自动扩成架构重写。

- 从可观察行为建立验收，避免仅根据当前实现补出必然通过的测试。需求可疑时回到原始请求核对。
- 运行与改动相关的测试、错误路径及必要回归。性能比较保持负载和统计口径一致；UI 验收包括交互与相关尺寸，不只截图。
- 候选代码各自通过后，仍检查整合版本的接口和用户路径。保留失败证据、实际输出和必要的环境限制。
- 测试覆盖有限、外部服务不可访问等缺口明确标出，不能用编译成功替代全部验收。部署是否执行取决于任务授权。

## 内容与实现混合的任务

分别设置内容验收与实现验收，再检查二者衔接。例如内容网站需核对事实、术语与目标结构，也需核对渲染、交互、下载和语言切换是否忠实保留内容。只检查本次范围内相关路径，不因混合任务扩展产品功能。

两类条件都在范围内时，任一必要条件失败都不能整体记为 VERIFIED。记录通过、未知和失败分别属于内容还是实现，避免一侧通过掩盖另一侧缺口。
