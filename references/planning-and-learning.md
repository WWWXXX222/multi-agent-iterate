# 重规划与经验复用

在复杂任务需要重规划、自主排障或沉淀纠正时读取。复用现有契约、检查点和项目记录；文件名不是方法本身。

## 计划包含验证

先确认关键来源、现状与可执行的验收入口，再列少量可勾选步骤：实施什么、依赖什么、怎样确认结果。每一步指向可观察产物；进度只按实际证据更新。验证工具、数据或环境缺失时，先尝试在范围内补齐；无法解决的记录为未知，不等写完后才发现无法验收。

计划随任务规模缩放。方向明确的小修改直接处理；复杂任务也不需要每个阶段停下来等用户确认。原有授权持续有效，真正影响方向且无法从资料或实验解决的取舍才询问。

## 何时重新规划

触发条件是前提失效，不是任何一次测试失败：关键来源否定了假设、接口或依赖改变、同一失败在重复修补后仍无新证据，或投入明显偏离剩余预算。

1. 保存当前工作和最佳已验证版本，指出哪条假设失效及直接证据。
2. 查根因，提出能区分旧假设与新假设的最小检查；有证据后修订受影响步骤，保留仍有效的工作。
3. 更新契约与相关 worker 的输入版本；暂停或改派依赖旧前提的任务，不接收过期分片直接合并。独立工作可继续。
4. 在同一预算内继续验证。若需改变已确认目标或范围，先呈现取舍；不自行降标，也不把重规划当成新增轮次额度。

例如文档中的两个收入目标实际口径不同，应回到来源厘清定义与单位，再修订相关指标及双语表述；只统一措辞解决不了问题。例子只说明诊断方式，不预设业务结论。

## 自主修复要留下证据

在用户授权的修复范围内，主动读取错误、相关日志、原始材料或失败测试，建立可复现的失败现象；修复后重跑对应检查及必要回归。无法复现时说明已观察到什么、尚缺什么，不凭猜测宣布根因。

编译通过、屏蔽报错、删除失败测试或降低目标不能代替修复。需要新增测试时，测试应刻画用户行为或真实失败；已有检查足够时直接复用。文档对应的是源文对照、计算和读者问题，不强行套代码测试。

“更简洁”也需要收益证据：比较能否保留同一行为/约束，同时减少维护成本或阅读歧义。复杂度仅从一处转移到另一处、扩大范围或破坏既有约束的重写，不作为改进。

## 让纠正影响下一次执行

- **先区分变化性质**：用户新增需求是新的决定，记录取代关系；真实误解或重复失败才提炼经验。名称、文风等偏好保留其适用范围。
- **记录到合适位置**：任务局部记录放在契约/运行日志。可复用的项目经验复用已有项目记录或本次运行目录中的经验段落；不自动修改全局 `AGENTS.md`、`CLAUDE.md`、其他 skill 或公共仓库。
- **每条经验可执行**：`适用条件 → 错误/纠正及证据 → 下次动作 → 如何确认有效`。附日期与来源；少量即可，不记录空泛的“以后更仔细”。
- **实际复用与修剪**：开始或恢复相关任务时只读适用条目；重复项合并，新证据推翻旧规则时留痕更新。仅写入经验文件不等于已防止复发。
- **推广需要验证**：通用 skill 更新限于用户授权的维护范围，用真实失败回放或新案例检验。未做对照实验，不宣称错误率下降或效率提升倍数；私有案例不随公开 skill 发布。

不强制创建 `tasks/lessons.md` 或第二套任务管理目录。目标是让下一次执行改变，而非让规则文件越来越长。
