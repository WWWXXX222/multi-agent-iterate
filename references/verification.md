# 验证与收敛

在建立运行契约时读。把“更好”变成能检查的具体条件，验证强度随任务影响与不确定性调整。文档、coding 与混合任务的具体要求见 [任务验收](task-acceptance.md)。

## 建立验证地图

每个关键条件记录四件事：要观察什么、去哪里找/如何复现、通过条件是什么、证据在哪里。默认不需要新平台或统一脚本。

| 任务 | 可以验证什么 | 不应声称什么 |
| --- | --- | --- |
| 方案 / OKR | 原始决定是否保留、来源能否追溯、口径是否一致、责任与容量是否冲突、验收是否可执行 | 审稿通过证明商业目标一定达成；建议数值等于已批准承诺 |
| 研究 | 原文是否支持结论、数据窗口与分母是否一致、反证是否被遗漏、推导能否重算 | 多篇转载是独立证据；模型共识消除资料冲突 |
| 产品 / UI | 真实任务能否完成、信息层级、可访问性、状态切换和屏幕尺寸下的行为 | 截图看起来正确就证明所有交互正确 |
| 代码 / 性能 | 用户可观察行为、相关回归、同负载下前后测量、指标噪声和副作用 | 能编译或 worker 自报 PASS 就证明问题已解决 |
| 文稿 | 必需信息完整、逻辑与术语一致、对读者行动有帮助、长度要求是否满足 | 评分更高或文字更多就代表质量更好 |

有现成验证器时先复用。缺少重复检查能力时才补最小工具，并证明它能识别至少一个已知失败或前后差异。一次简单润色不强制新测试框架；没有可运行验收器时，使用明确的证据核对并披露限制。

## 证据纪律

- 保留原始基线与版本；每条验证绑定实际文件版本、提交或快照，不验 A 却发布 B。
- 区分用户明确决定、原始事实、历史讨论、计算结果、估计和 agent 建议。来源较新不自动覆盖更明确的决定；矛盾留痕。
- 对数值记录单位、期间、分母、适用对象；目标变更保留前值、理由、影响和确认状态。
- 所有候选在相同条件下检查。性能比较固定负载与采样方式；通过条件不能因候选失败而放宽。
- 固定验收不等于固定目录或解法。发现新的结构性缺陷时记录新增条件及理由，对基线和所有保留候选同样检查，不能借重分类删掉原约束。
- 最终整合稿必须验证：候选分别通过不代表融合后通过。对真实产物运行或查看，必要时交叉核查证据来源。

## 评审发现与裁决

建议字段：`ID | 位置/版本 | 发现 | 来源或复现 | 对目标的影响 | 具体改法 | 验证办法 | 收益/代价 | 主控裁决 | 结果`。可以用简短段落记录，不强制宽表格。

主控裁决的含义：

- **修复**：证据支持、属于范围、影响交付，当前轮处理。
- **条件建议**：可能有用，但收益/代价或事实条件尚不清楚；先做小验证或作为取舍呈现。
- **待核或待决**：需要外部输入或用户决定；说明影响，继续不依赖它的部分。
- **拒绝**：与证据冲突、越界、重复或仅偏好；写一句可复核理由。

不要按票数自动通过或自动改稿；严重的单人发现也可能成立，多个 reviewer 也可能共用错误前提。相同根因合并；相互矛盾的发现回到来源或最小实验。

## 每轮的最小账本

| 轮次/版本 | 问题或假设 | 本次改变 | 前后证据 | 保留/撤回及原因 | 未决事项 |
| --- | --- | --- | --- | --- | --- |

无实质改善包括：纯换词但没有解决约定问题；增加没有独立价值的流程/文件；同一发现无新证据地循环讨论。表述清晰度若本身是用户目标，则可用读者任务、歧义消除等证据说明改善，而非一律视为装饰。

优先保存当前最佳已验证版本，失败尝试另存简短记录。撤回仅限本次工作，不覆盖用户或其他 agent 的合法改动。用户精确要求的轮数可以以“复核后无需修改”完成，不能伪造实质提升。

## 结束结论

按 `SKILL.md` 的完成、预算、指定轮次和停滞规则结束。检查点同时写 `stop_reason` 与 `quality_status`；这是本 skill 的产物字段，不是运行平台的 goal 状态 API。

`VERIFIED` 需要当前稿满足所有约定可验条件；`CONDITIONAL` 需要推荐稿已可审阅但依赖外部事实/判断；`INCOMPLETE` 表示必要工作或已知失败仍未处理完。不会因为“第三轮到了”就把失败改成通过。

交付包括实际变化、证据与关键残留条件。没有条件支持时，不把建议作为批准，也不把暂时观察到的结果推广成长期保证。

## Skill 维护时的回放验证

仅在创建、更新或评测本 skill 的授权范围内进行，使用隔离目录，默认不修改业务原件或调用外部写入。普通业务迭代不附带此流程。

1. **留出案例**：准备反馈发生前的需求、原始资料与初稿，隔离后续用户反馈和最终修订。确认候选 skill、示例、输入路径和继承上下文没有泄露该案例的答案。用于制定规则的案例只能称为回归案例；评测主动发现能力需另选未参与制定规则的案例。
2. **固定条件**：提前记录任务范围、模型、agent/轮次预算和评价方法。要声称新版优于旧版，需让两个版本在相同输入和预算下实际运行；没有对照只报告本次观察。
3. **检查实际产物**：看是否主动发现了同类关键问题、建议能否直接执行、有何证据及取舍，是否保留约束、引入错误或无收益重构。不要求分类名称或措辞与用户答案一致；有充分理由的替代解法也可成立。
4. **检查迁移与克制**：加入另一类任务及一个明确的小修改，观察是否把某个案例的分类硬套到所有工作，或为简单任务启动多余流程。用多少案例就如实报告多少，不把一次成功扩成稳定效果保证。

人工后续反馈也是比较材料，不是绝对真值。若历史资料不完整、评测者已看到答案或无法隔离上下文，披露这些限制，不声称盲测。保存提示词、版本、实际产物与评审依据；不将真实公司资料或评测答案随公开 skill 发布。
